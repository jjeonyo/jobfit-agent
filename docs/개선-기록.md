# 개선 기록

이 프로젝트의 문제, 원인, 조치, 검증 방법, 남은 일을 기록한다. 새 문제를 찾거나 조치하면
여기에 먼저 적고 코드를 고친다.

원칙:
- 수치는 실측값만 쓴다. 측정 전에는 칸을 비워둔다 (README 핵심 불변 규칙 4).
- "조치함"과 "효과 확인됨"을 구분한다. 평가셋으로 재측정하기 전까지 조치의 효과는 확인되지 않은 것이다.
- 항목마다 증상 → 원인(코드 위치) → 영향 → 조치 → 검증 → 상태 순으로 적는다.

## 해결된 문제

### P1. Gap Planner 경로로 검증 원장 우회

- 증상: 검증에서 차단될 판정의 설명이 리포트의 준비 계획 문장으로 나올 수 있었다.
- 원인: 그래프 순서가 대조 → 갭 → 검증이었다. Gap Planner가 검증 전 판정의 rationale
  (예: 인용 없는 "Kafka 실무 3년")을 입력으로 받았다.
- 영향: 핵심 불변 규칙 2("인용 없는 주장은 노출하지 않는다", "Verifier를 우회하는 경로는 만들지 않는다") 위반.
- 조치: 순서를 대조 → 검증 → 갭으로 바꿔 Gap Planner는 검증을 통과한 판정만 받는다 (`app/graph.py`).
  재생성할 때 갭을 다시 호출하던 비용도 없어졌다.
- 검증: `tests/test_pipeline.py::test_gap_planner_never_sees_blocked_rationale`

### P2. 존재하지 않는 청크 id 인용이 검증 통과

- 증상: `citations: ["chunk-999"]`처럼 이력서에 없는 청크를 인용해도 통과했다.
- 원인: 검증 원장이 `citations`가 비어 있는지만 확인했다.
- 조치: 현재 이력서 청크에 없는 id를 하나라도 인용하면 판정 전체를 차단한다 (`app/agents.py` `verify`).
- 검증: `tests/test_pipeline.py::test_citation_to_unknown_chunk_is_blocked`

### P3. 재생성이 같은 프롬프트를 반복

- 증상: 검증 원장이 재생성을 요청해도 결과가 거의 바뀌지 않을 구조였다.
- 원인: temperature 0인 상태로 모든 요건을 같은 프롬프트로 다시 판정했다.
- 조치: 차단된 요건만 재검증 지시(`MATCHER_RETRY_NOTE`)를 붙여 다시 판정하고, 통과한 판정은 유지한다.
- 검증: `tests/test_pipeline.py::test_fabricated_claim_is_retried_then_marked_unverified`

### P4. 판정 누락·스키마 위반·코드펜스 출력 시 500

- 원인: LLM 출력 항목을 바로 pydantic 모델로 만들었다. 실패하면 예외가 그대로 올라갔다.
- 조치: 코드펜스를 허용하고, 스키마 위반 항목은 버린다. 판정이 빠진 요건은 재생성 대상으로
  잡고, 그래도 없으면 unverified로 넘긴다. 파싱이 두 번 실패하면 502를 반환한다.
- 검증: `tests/test_pipeline.py::test_missing_and_invalid_items_are_regenerated`,
  `test_fenced_json_is_parsed`, `test_analyze_unparseable_llm_output_returns_502`

### P5. 요건 추출 정확도를 요건 id 일치로 계산

- 증상: 요건 개수만 맞으면 내용과 무관하게 정확도가 높게 나왔다.
- 원인: Parser는 id를 `req-01`부터 순서대로 붙이는데, 정답 id와 집합 비교를 했다.
- 조치: 요건 문장의 문자 bigram Dice 유사도로 1:1 대응시킨다 (기본 임계값 0.5, `eval/run.py`).
- 검증: `tests/test_logic.py::test_extraction_accuracy_aligns_by_content_not_id`.
  예시 파일에서 기존 방식으로 1.0이던 케이스가 0.5로 나오는 것을 확인했다.

### P6. 판정 정확도를 측정할 수 없음

- 원인: 판정 정확도를 계산하는 코드가 없었다. 정답 파일에 판정을 적을 칸도 없었다.
- 조치 (`eval/run.py`):
  - 정답 요건에 `verdict`·`citations`를 적는다 (선택).
  - 대응한 요건끼리 판정을 비교해 아래 지표를 낸다.

  | 지표 | 정의 | 목표 |
  | --- | --- | --- |
  | `verdict_accuracy` | 정답 판정과 예측 판정이 같은 비율. 미검증은 오답 | 높을수록 |
  | `fabrication_rate` | 정답이 '없음'인 요건을 '매칭/부분 매칭'으로 판정한 비율 (지어내기) | 0 |
  | `unverified` | 예측이 미검증인 건수 | 낮을수록 |
  | `citation_accuracy` | 정답·예측이 모두 매칭/부분 매칭이고 정답 인용이 있을 때, 예측 인용이 정답 인용과 겹치는 비율 | 높을수록 |
  | `confusion` | 정답 판정(행) × 예측 판정(열, 미검증 포함) 건수 | — |

  - 분모가 0이면 0.0이 아니라 `null`(측정 불가)로 낸다.
- 결정: 미검증을 정답에서 빼면 시스템이 판정을 내지 못한 경우가 정확도를 부풀린다.
  그래서 오답으로 계산하고 건수를 따로 낸다.
- 검증: `tests/test_logic.py::test_verdict_metrics_*`

### P8. 예측 파일을 만드는 수단이 없음

- 조치: `eval/predict.py`는 정답 파일의 공고마다 파이프라인을 실행해 예측 파일을 만든다.
  케이스별 LLM 호출 수, 응답 시간, 차단 건수도 기록하며, `eval/run.py`가 이를 집계한다.
- 검증: `tests/test_predict.py`

### P12. 비용(토큰 사용량)을 측정하지 않음

- 증상: README 측정 지표의 "비용"을 채울 수단이 없었다. LLM 호출 수와 응답 시간만 기록했다.
- 원인: `_call_json`이 LLM 응답에서 본문(`content`)만 읽고 토큰 사용량은 버렸다.
- 조치:
  - `_call_json`이 응답의 `usage_metadata`에서 입력·출력 토큰 수를 읽어 호출 횟수와 함께 반환한다.
  - 노드는 `_add_usage`로 상태에 누적한다. JSON 파싱 재시도와 재생성 호출도 포함된다 (`app/agents.py`).
  - `Report`에 `input_tokens`, `output_tokens`를 넣었다. `/analyze` 응답과 예측 파일에 들어간다.
  - `eval.run`의 `pipeline`이 `mean_input_tokens`, `mean_output_tokens`를 낸다. 오류 케이스는 평균에서 뺀다.
  - `usage_metadata`가 없는 응답은 0으로 세고 경고 로그를 남긴다. 실측 중 이 경고가 나오면 토큰 값은 과소 집계다.
- 검증:
  - `tests/test_pipeline.py::test_token_usage_is_summed_over_all_calls_including_retries`,
    `test_missing_token_usage_counts_zero_and_warns`
  - `tests/test_predict.py::test_predict_case_records_report_and_elapsed`
  - `tests/test_logic.py::test_evaluate_reports_mean_token_usage_excluding_error_cases`
  - 실제 `ChatOpenAI`에 OpenAI 응답 형식의 가짜 HTTP 응답(`usage.prompt_tokens=123`,
    `completion_tokens=45`)을 주고 `_call_json`이 입력 123·출력 45를 반환하는 것을 확인했다.
- 남은 일: 비용(원·달러)은 코드로 계산하지 않는다. 단가가 바뀌므로 실측 때 평균 토큰 수 × 그날 단가로
  계산하고 쓴 단가를 함께 기록한다.

## 조치했으나 효과를 확인하지 못한 문제

### P7. 판정 프롬프트와 라벨 기준이 다름

- 증상: 정답 라벨은 `docs/판정-기준.md`로 다는데, 모델은 다른 기준으로 판정했다.
- 원인: 기존 Matcher 프롬프트에 없던 것:
  - '부분 매칭'의 정의
  - "애매하면 부분 매칭" 규칙
  - "학습 중은 경험이 아님" 규칙
  - 근무조건 처리 규칙
- 영향: 기준 차이가 그대로 판정 오답으로 잡힌다. 특히 이력서의 "학습 중 … CI/CD"
  (`data/profile.md:23`)를 근거로 CI/CD 요건을 '부분 매칭'으로 판정할 수 있다.
- 조치: 판정 정의와 고정 규칙을 `VERDICT_RULES` 한 곳에 두고 Matcher 프롬프트에 넣었다.
  `docs/판정-기준.md`도 같은 문장으로 맞추고, 일치 여부를 테스트로 확인한다
  (`tests/test_logic.py::test_verdict_rules_match_labeling_doc_and_prompt`).
- 측정 전에 바꾼 이유: 프롬프트와 라벨의 기준이 다르면, 그 상태에서 잰 수치는 모델 성능이
  아니라 기준 차이를 잰 것이 된다.
- 효과 확인 방법:
  1. 평가셋으로 현재 코드와 이전 프롬프트 커밋(`bf2d215`)에서 각각 `eval.predict`를 실행한다.
  2. 같은 정답 파일로 `eval.run` 결과를 비교한다.
- 상태: 효과 미측정.

### P9. 검증 원장이 인용 내용의 뒷받침 여부를 보지 않음

- 증상: 실제 이력서에 있는 청크를 인용하기만 하면, 그 청크가 주장을 뒷받침하지 않아도 통과했다.
- 원인: 검증 원장이 인용이 있는지, 그 id가 이력서에 있는지만 확인했다.
- 재현 시나리오: CI/CD 요건에 대해 "학습 중 … CI/CD" 문장이 든 청크를 인용하고
  '부분 매칭'으로 판정하면 차단되지 않았다.
- 영향: 검증 원장을 통과한 지어내기가 리포트에 나갈 수 있다 (핵심 불변 규칙 1).
- 대응 후보:

  | 후보 | 방식 | 추가 LLM 호출 | 상태 |
  | --- | --- | --- | --- |
  | (a) 근거 문장 원문 대조 | Matcher가 인용한 청크마다 근거 문장(quote)을 글자 그대로 복사해 내고, 검증 원장이 원문에 있는지 문자열로 확인 | 없음 | 적용 (`72bda60`) |
  | (b) 뒷받침 판정 노드 | 요건·판정·근거 문장을 주고 "이 문장이 이 판정을 뒷받침하는가"를 LLM으로 판정 | 분석 1건당 +1회 | 보류 |

- 조치 (a): `app/agents.py`의 `block_reason`은 '매칭/부분 매칭' 주장이 아래 조건을 모두 만족할
  때만 통과시킨다. 차단 사유는 요건별로 재생성 프롬프트에 들어간다 (`fix_reasons`).
  1. 인용이 있고, 모두 현재 이력서의 청크다.
  2. 인용한 청크마다 근거 문장이 하나 이상 있다.
  3. 근거 문장은 10자 이상(`MIN_QUOTE_CHARS`)이고, 그 청크 원문에 글자 그대로 있다
     (공백 차이만 무시).
  4. 근거 문장이 든 목록 항목에 '학습 중'(`NON_EXPERIENCE_MARKERS`) 표기가 없다.
- 구현 중 발견한 것: 4번을 근거 문장 안에서만 확인하면 "Airflow, 클라우드, CI/CD"만
  인용해 표기를 피할 수 있다. 그래서 근거 문장이 든 목록 항목 전체를 본다. 또 실제 이력서에서
  이 항목은 chunk-001과 chunk-002 경계에 걸려 있다. chunk-002는 표기 뒤에서 시작하므로,
  청크 안에서만 보면 chunk-002 인용이 통과했다. 그래서 청크에 전체 본문 내 위치(`start`)를
  기록하고(`app/chunking.py`), 검증 원장이 전체 본문을 복원해 항목 시작을 찾는다.
  청크 id와 본문은 바뀌지 않았다.
- 검증:
  - `tests/test_quotes.py`: 조건별 차단, 공백 차이 허용, 같은 청크의 다른 항목은 통과,
    청크 경계 사례, 재생성 프롬프트의 차단 사유, 의역한 근거 문장을 재생성으로 바로잡는 흐름.
  - 실제 `data/profile.md` 청크에 대해 다음을 확인했다.
    - "Airflow, 클라우드, CI/CD", "잡핏 에이전트 프로젝트로 실전 경험으로 전환 중"은
      chunk-001과 chunk-002 모두에서 차단된다.
    - 그 밖의 항목(머리말, 기술 스택, 경력, 프로젝트, 자격)에서 뽑은 근거 문장 8개는 통과한다.
  - 가짜 LLM으로 웹 UI를 띄워 확인했다. 근거 문장이 판정 카드에 표시되고, '학습 중' 문장을
    인용한 판정은 4회(최초 + 재생성 3회) 차단된 뒤 미검증으로 바뀐다.
- (a)로 못 잡는 경우:
  - 원문에 실제로 있지만 요건과 무관한 문장을 근거로 댄 경우.
    예: Kafka 요건에 "Python FastAPI와 Java Spring Boot 양쪽 백엔드 개발 가능"을 인용.
    문자열 검사로는 관련성을 판단할 수 없다.
  - '학습 중' 외의 비경험 표기. 이력서에 새 표기를 쓰면 `NON_EXPERIENCE_MARKERS`에 추가해야 한다.
  - 목록 항목은 마크다운 목록 기호(`-`, `*`, `>`, `#`)로 구분한다. 이력서 형식이 바뀌면
    항목 구분이 달라진다.
- (b) 결정 기준 (실측 후):
  - `fabrication_rate` > 0이고, 해당 오류의 근거 문장이 원문에 있지만 요건과 무관하면 (b)를 검토한다.
  - (b)를 적용하면 LLM 호출 수·응답 시간 변화를 "실측 기록"에 함께 적는다.
- 상태: (a) 적용, 효과 미측정.

## 미해결 문제

### P10. 요건 대응이 어휘 기반 (알려진 한계)

- 동의어("커뮤니케이션"/"의사소통", 유사도 0.33)는 대응시키지 못한다.
- 핵심어 하나만 다른 문장("AWS 클라우드 운영 경험"/"GCP 클라우드 운영 경험", 0.70)은 대응시킨다.
- 보완: 정답 `text`는 공고 문구를 그대로 옮긴다. `eval.run` 출력의 `per_case`에서
  `alignment`와 `unmatched_gold_ids`를 육안으로 확인한 뒤 수치를 기록한다.
- 바꿀 조건: 육안 검토에서 잘못된 대응이 반복되면 임베딩 유사도로 바꾸는 것을 검토한다.
  이 경우 평가에 API 비용이 들고 결과가 모델에 따라 달라진다.

### P11. 정답 인용이 이력서 청킹에 묶여 있음 (알려진 한계)

- 청크 id는 `data/profile.md`를 1,000자/중첩 100자로 나눈 순번이다. 이력서를 고치면 청크
  경계가 바뀌어, 정답 `citations`가 다른 내용을 가리킬 수 있다.
- 보완: 이력서를 고친 뒤에는 `GET /chunks`로 청크를 확인하고 정답 인용을 다시 맞춘다.

### P13. 키워드 검색이 한국어 조사를 구분 (알려진 한계, 현재 영향 작음)

- `app/rag.py`의 `_tokens`는 "경험이"와 "경험"을 다른 토큰으로 본다.
- 현재 이력서는 청크 5개이고 요건마다 최대 5개를 가져오므로, 토큰이 하나라도 겹치는 청크는
  모두 프롬프트에 들어간다. 그래서 지금은 영향이 작다.
- 바꿀 조건: 이력서가 길어져 청크 수가 `top_k`를 넘거나, 실측에서 정답 '매칭'이 '없음'으로
  나오는 과소 판정의 원인이 검색 누락으로 확인되면 벡터 검색을 켜거나 `top_k`를 늘린다.

### P14. 근거 문장 검사로 정당한 판정까지 차단될 위험 (감시)

- 원인: P9 (a)는 근거 문장이 원문과 글자 그대로 같아야 통과한다. 모델이 문장부호·조사를
  바꾸거나 두 청크에 걸친 문장을 인용하면, 근거가 실제로 있어도 차단된다.
- 영향: 미검증이 늘고, 재생성으로 LLM 호출 수와 응답 시간이 늘어난다.
- 현재 대응: 차단 사유("근거 문장이 chunk-00N 원문에 없음: …")를 재생성 프롬프트에 넣어
  모델이 고칠 수 있게 했다.
- 감시 방법: 실측에서 다음을 본다.
  - `verdict.unverified`와 `verdict.confusion`의 "정답 매칭/부분 매칭 → 예측 미검증" 건수
  - `pipeline.mean_llm_calls`
- 바꿀 조건: 정당한 판정이 미검증으로 빠지는 사례가 반복되면, 차단 사유별 빈도를 기록하고
  비교 방식을 완화할지 검토한다. 예: 문장부호를 무시하고 비교한다.
