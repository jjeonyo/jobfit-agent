# 판정 기준 (평가셋 정답 라벨 작성용)

평가셋 정답 라벨(`eval/cases/*.json`)을 직접 작성할 때 쓰는 기준이다.
Matcher 프롬프트와 Verifier가 지키는 규칙을 그대로 따른다. 기준이 바뀌면
이 문서를 먼저 고치고 라벨을 다시 맞춘다.

## 판정 3종

| 판정 | 기준 | 인용 |
| --- | --- | --- |
| 매칭 | 이력서 원문에 요건을 직접 충족하는 경험·기술이 적혀 있다. | 필수 — 근거 청크 id |
| 부분 매칭 | 관련 경험은 원문에 있으나 요건의 범위·수준·기간 중 일부만 충족한다. | 필수 — 근거 청크 id |
| 없음 | 원문에 근거가 없다. | 비움 |

## 고정 규칙

1. **애매하면 '부분 매칭'으로 한다.** 매칭과 부분 매칭 사이에서 판단이 갈리면
   부분 매칭으로 내린다. 부분 매칭과 없음 사이에서 갈리면, 원문에 인용할 문장이
   있을 때만 부분 매칭이고 없으면 없음이다.
2. **인용할 문장이 없으면 '없음'이다.** 추론("FastAPI를 썼으니 비동기도 알 것이다")은
   근거가 아니다.
3. **'학습 중' 항목은 경험이 아니다.** 이력서에 학습 중으로 표기된 기술(예: Airflow,
   클라우드, CI/CD)은 경험 요건에 대해 '없음'으로 판정한다.
4. **팀 작업은 팀 작업으로 본다.** 공동 개발한 부분을 '단독' 경험으로 판정 근거에
   쓰지 않는다. 담당 범위가 원문에 적힌 만큼만 근거로 쓴다.
5. **근무조건의 '없음'은 '불충족'이 아니다.** 근무지·고용 형태처럼 이력서로 판단할 수
   없는 조건은 근거가 없다는 뜻으로 '없음'을 쓴다.

## 라벨 작성 절차

1. 공고 원문을 `posting_text`에 붙여넣는다 (크롤링하지 않는다).
2. 요건을 직접 뽑아 `gold_requirements`에 적는다. 회사 소개·복리후생 문구는 요건이 아니다.
3. 요건마다 위 기준으로 판정과 근거 청크 id를 정한다. 청크 id는 `GET /chunks`로 확인한다.
4. 판단이 갈린 요건은 아래 "판정 사례"에 한 줄로 남긴다.

참고: `eval/run.py`는 예측 요건과 정답 요건을 id가 아니라 요건 문장 유사도로 대응시킨다.
그래서 `gold_requirements`의 `text`는 공고 문구를 그대로 옮겨 적는다 (요약·의역하면
대응이 안 될 수 있다). 현재는 요건 추출 정확도와 근거 인용률만 계산하고, 판정 정확도는
계산하지 않는다.
